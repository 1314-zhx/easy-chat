# 配置热更新与服务平滑重启改造说明

## 背景

项目原先的配置均在服务启动时通过本地 YAML 文件加载，运行期间不会自动刷新。对于 AI、WebSocket、MQ 等服务而言，以下参数一旦调整就需要重启服务才能生效：

- 群聊已读回执合并阈值
- 合并推送延迟时间
- RAG 检索参数
- 指代消解开关
- 记忆抽取开关

同时，服务退出时也缺少统一的优雅停机机制，可能导致：

- WebSocket 长连接被直接中断
- Kafka 消费未完成就退出
- 正在处理的请求丢失
- 运行中协程未能释放

本次改造的目标是：

1. 为核心服务补充配置热更新能力
2. 为核心服务补充平滑退出能力
3. 尽量保持对现有业务结构的低侵入改造

---

## 改造范围

本次改造覆盖以下服务：

- `apps/ai/rpc`
- `apps/im/ws`
- `apps/task/mq`

并新增了若干公共基础设施模块：

- `pkg/etcdwatch`
- `pkg/runtimeconfig`
- `pkg/lifecycle`

---

## 新增的公共能力

### 1. `pkg/etcdwatch`

新增 etcd 配置监听器，用于监听配置 key 的变化，并在配置更新后触发回调。

核心能力：

- 基于 etcd `Watch` 监听指定 key
- 支持 JSON 配置反序列化
- 便于各服务接入动态配置刷新

适用场景：

- AI 服务 RAG 参数刷新
- WS 服务消息合并阈值刷新
- MQ 服务合并推送策略刷新

---

### 2. `pkg/runtimeconfig`

新增运行时配置承载结构，用于保存热更新后的配置值。

设计原则：

- 启动时读取本地 YAML 作为默认配置
- 运行期间由 etcd watcher 刷新
- 业务逻辑通过 runtime config 读取最新值

这样可以避免直接修改 `ServiceContext.Config`，降低对现有逻辑的侵入。

---

### 3. `pkg/lifecycle`

新增生命周期控制器，用于支持 draining 与优雅退出。

主要能力：

- 标记服务进入 draining 状态
- 记录后台任务生命周期
- 提供停止信号通道
- 便于服务退出前等待当前任务完成

适用场景：

- WebSocket 服务平滑下线
- Kafka 消费者停机
- AI 服务资源释放

## AI 服务改造

### 修改文件

- `apps/ai/rpc/ai.go`
- `apps/ai/rpc/internal/svc/servicecontext.go`

### 改造内容

#### 1. 增加 etcd 配置监听

AI 服务启动后会监听：

- `/config/ai.rpc`

当该 key 发生变化时，服务会：

- 反序列化新配置
- 更新运行时配置对象
- 让后续逻辑读取最新参数

#### 2. 增加运行时配置持有对象

在 `ServiceContext` 中增加运行时配置持有能力：

- `ApplyRuntimeConfig(...)`
- `RuntimeConfig()`

这样后续可把 RAG、MCP、Qwen 相关参数切换为动态读取。

### 当前状态

目前 AI 服务已经具备热更新接入点，但还需要把更多业务代码逐步切换为读取 `RuntimeConfig()`，才能让所有参数真正热生效。

## WS 服务改造

### 修改文件

- `apps/im/ws/im.go`
- `apps/im/ws/internal/svc/servicecontext.go`

### 改造内容

#### 1. 增加 etcd 配置监听

WS 服务启动后会监听：

- `/config/im.ws`

当该配置 key 变化时，会更新运行时配置对象。

#### 2. 增加 draining 与优雅退出

WS 服务在收到退出信号后：

- 标记进入 draining 状态
- 延迟等待一段时间
- 再关闭 WebSocket server

这个过程可以减少正在传输中的消息被强制中断的概率。

### 当前状态

WS 服务已经具备热更新和优雅退出的基础接入能力，后续还可以继续把 ACK、已读回执、连接空闲时间等参数接入动态配置。

## MQ 服务改造

### 修改文件

- `apps/task/mq/task.go`

### 改造内容

#### 1. 增加优雅退出骨架

MQ 服务收到 `SIGINT` / `SIGTERM` 后：

- 进入 draining
- 延迟等待当前任务自然收敛
- 再执行退出

#### 2. 为 Kafka 消费器平滑停机打基础

当前项目使用 `kq.MustNewQueue(...)` 启动 Kafka 消费者。
后续如果继续细化，可以再补一层消费包装器，用于：

- 停止拉取新消息
- 等待当前批次处理完成
- 再提交 offset
- 再退出进程

### 当前状态

MQ 服务已接入退出控制骨架，后续仍建议进一步增强 Kafka 消费者的精细化停机逻辑。

## 配置中心设计建议

本次热更新方案采用的是 **etcd 作为配置中心** 的思路。

建议配置 key 规划如下：

- `/config/ai.rpc`
- `/config/im.ws`
- `/config/task.mq`

建议配置内容采用 JSON 或 YAML 格式保存。

### 静态配置

以下配置仍建议保留在本地 YAML 中，启动时加载：

- Mongo 地址
- Redis 地址
- Kafka 地址
- etcd 注册地址
- 监听端口

### 动态配置

以下配置适合热更新：

- 群聊已读合并阈值
- 合并延迟时间
- RAG TopK
- RAG 相似度阈值
- 最近历史窗口大小
- 话题跟踪开关
- 记忆抽取开关

---

## 配置热更新流程

1. 服务启动时读取本地 YAML
2. 创建 `ServiceContext`
3. 启动 etcd watcher
4. 监听配置 key 的变化
5. 收到新配置后进行反序列化和校验
6. 更新运行时配置对象
7. 后续业务逻辑读取最新值

---

## 平滑重启流程

1. 新实例先启动并完成注册
2. 旧实例收到退出信号后进入 draining
3. 停止接收新请求
4. 等待当前请求和后台任务结束
5. 释放资源并退出

对于不同服务，平滑退出策略略有差异：

- **AI RPC**：重点是完成当前 gRPC 请求再退出
- **WS**：重点是保留已有连接，减少强制断连
- **MQ**：重点是处理完当前消费批次再退出

## 后续优化建议

### 1. 将业务参数真正切换到 runtime config

当前已经有热更新接入点，但部分业务仍然在启动时读取一次配置。后续建议逐步切换为：

- AI RAG 参数走 runtime config
- WS 已读回执参数走 runtime config
- MQ 合并阈值走 runtime config

### 2. 进一步增强 MQ 平滑退出

建议给 Kafka consumer 外层再包一层可控 shutdown 逻辑，确保：

- 不再拉新消息
- 当前批次处理完再退出
- offset 正确提交

### 3. 清理测试目录的 main 冲突

建议将 `test/` 下的可执行脚本拆分为独立命令或迁移到单独目录，避免影响全量测试。

---

## 总结

本次改造完成了项目的两项基础能力建设：

1. **配置热更新**：通过 etcd watcher + runtime config，为 AI、WS 等服务提供动态参数刷新能力
2. **服务平滑重启**：通过 lifecycle/draining 机制，为 WS、MQ 等服务提供优雅退出能力

改造目标是尽量低侵入地接入到现有架构中，为后续参数动态化、灰度发布和服务升级打下基础。
